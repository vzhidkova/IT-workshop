# LogHive: Порядок действий при инциденте

## Общий порядок

1. Запишите время и признак, по которому поняли, что что-то не так.
2. Найдите инцидент в таблице ниже и выполните «Проверить», затем «Сделать».
3. Сообщите владельцу пострадавшей ВМ. Пользователям о сбое пишет Иванова А.
4. Когда признак исчез, проверьте результат и внесите запись в журнал инцидентов (шаблон в конце).

Если оповещения в Mattermost не приходят, а Grafana жива, смотрите панель Grafana напрямую: на неё можно положиться, даже когда канал молчит. Если решить не удаётся за 30 минут, зовите остальных участников команды.

## Быстрый выбор

| Что видите | Инцидент |
| --- | --- |
| Сайт не открывается, ошибка 502 или 504 | 1 |
| В панели ошибки 500, данные пропали, БД не стартует | 2 |
| Оповещение, что диск заполнен больше 80% | 3 |
| В LogHive нет новых записей из Mattermost | 4 |
| Ошибки в панели есть, а в канале errors тишина | 5 |
| Grafana не открывается, новые копии не появляются | 6 |
| Пароль или ключ попал в чат, репозиторий, скриншот | 7 |
| Резкий рост ошибок или поток оповещений | 8 |

## Инцидент 1. Сайт LogHive не открывается

**Признак.** Сайт не открывается или отвечает 502/504. Приходит оповещение Grafana о недоступности API (`probe_success` равен 0 дольше минуты, оповещение в течение 2 минут). Запрос `curl -i http://<IP_ВМ1>/api/health` не возвращает 200.

**Проверить.**

1. Включён ли у вас VPN. Если сайт не открывается только у одного человека, причина обычно в его VPN.
2. `ping <IP_ВМ1>`. Нет ответа при работающем VPN: упала ВМ 1, откройте её консоль в BASIS.
3. Зайдите на ВМ 1 по SSH и выполните `docker compose ps`: какие сервисы не в состоянии Up.
4. Отличите nginx от API. Запрос `curl -i http://localhost/` отвечает: nginx жив. Запрос `curl -i http://localhost/api/health` даёт 502 или 504: nginx жив, API не отвечает. Соединения нет вообще: не работает nginx.
5. Посмотрите `docker compose logs --tail=100 <сервис>`. Частые причины падения API: нет связи с БД, не заданы секреты в `.env`, закончился диск (`df -h`).

**Сделать.**

- ВМ упала: запустите её в BASIS, затем `docker compose up -d`.
- Упал один сервис: `docker compose up -d` или `docker compose restart <сервис>`.
- API падает из-за БД: инцидент 2. Из-за диска: инцидент 3.
- Проверка: `/api/health` отвечает 200, вход в панель работает, свежая запись видна.

**Отвечает.** Жидкова В. Если за 30 минут не решено, подключается Икромжонов Ш. (сеть, ufw).

## Инцидент 2. База потеряна или испорчена

**Признак.** В панели ошибки 500. В логах API ошибки подключения к БД или нет таблиц. Контейнер БД не стартует или постоянно перезапускается. Данные пропали.

**Проверить.**

```
docker compose ps
docker compose logs --tail=100 <сервис_БД>
docker exec $DB psql -U loghive -d LogHiveDB -c 'SELECT count(*) FROM events'
df -h /
```

Нужны таблицы users, issues, events, notification\_outbox. Полный диск тоже ломает БД (инцидент 3).

**Сделать.**

1. Запишите время начала: цель по простою не более 30 минут (RTO).
2. Остановите API, чтобы он не писал в испорченную базу: `docker compose stop <сервис_API>`.
3. Если БД просто остановилась, а данные целы, достаточно `docker compose up -d` и проверки количества записей. Восстановление не нужно.
4. Если БД ещё читается, сначала сохраните её текущее состояние: `docker exec $DB pg_dump -U loghive LogHiveDB | gzip > /tmp/before_restore.sql.gz`.
5. Восстановите из копии на ВМ 3 по пункту 4 Инструкции администратора, начиная с самой свежей часовой копии. Если она не загружается, берите предыдущую (хранятся 3 часовые и 7 суточных).
6. Проверьте количество записей в таблицах, запустите API, войдите в панель.
7. Запишите время окончания и время копии: потеря данных не должна превышать 1 часа (RPO).

**Отвечает.** Жидкова В. (восстановление). Иванова А. отвечает за копии на ВМ 3 и сообщает пользователям о потере данных за период после копии.

## Инцидент 3. Диск заполнен больше 80%

**Признак.** Оповещение Grafana в канале errors либо заметили при ежедневном осмотре. Опасность: БД перестаёт принимать записи, копии не создаются.

**Проверить.**

```
df -h /
sudo du -xh / --max-depth=2 2>/dev/null | sort -rh | head -15
docker system df
```

**Сделать.** Сначала общее для любой ВМ:

```
docker image prune -f
sudo journalctl --vacuum-time=14d
sudo apt clean
```

Каталог данных PostgreSQL вручную не чистить. Дальше по ВМ:

- **ВМ 1.** Проверьте, что записи старше 14 дней удаляются \[механизм уточнить у Жидковой В.\]. Если диск растёт из-за всплеска ошибок, это инцидент 8.
- **ВМ 2.** Крупные файлы логов контейнеров: `sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -rh | head`. Размер очереди агента при долгой недоступности API.
- **ВМ 3.** В каталоге копий должно лежать 3 часовые и 7 суточных, самые старые лишние удалите. Метрики Prometheus хранятся 15 дней: если растут быстрее ожидаемого, сократите срок или запросите у преподавателя больше диска.

Проверка: занято меньше 80% и значение не растёт в Grafana в течение суток.

**Отвечает.** Владелец той ВМ, на которой заполнен диск.

## Инцидент 4. Логи перестали приходить

**Признак.** В панели LogHive нет новых записей из Mattermost, хотя Mattermost работает. Агент на ВМ 2 читает логи контейнера Mattermost и отправляет их в API на ВМ 1 (`POST /api/logs`); если API недоступен, он копит очередь у себя.

**Проверить (на ВМ 2).**

1. Жив ли Mattermost: `curl -i http://localhost:8065/api/v4/system/ping` и `docker compose ps`. Если Mattermost не работает, логов из него нет, это не ошибка агента.
2. Логи агента: `docker compose logs --tail=50 <агент>`. Ответ 401 или 403 значит неверный ключ приёма; отказ соединения или таймаут значит, что API недоступен.
3. Достижим ли API с ВМ 2: `curl -i http://<IP_ВМ1>/api/health`. Не отвечает: инцидент 1 или закрыт порт в ufw.
4. Свободное место: `df -h /`, очередь агента может его съесть.

**Сделать.**

- Упал агент или Mattermost: `docker compose up -d`, при необходимости `docker compose restart <агент>`.
- Неверный ключ: замените его по пункту 5 Инструкции администратора.
- Проверка: за 1–2 минуты в панели появились новые записи из Mattermost.

**Отвечает.** Икромжонов Ш. (ВМ 2, Mattermost) и Жидкова В. (агент).

## Инцидент 5. Не приходят оповещения в Mattermost

**Признак.** В панели есть записи ERROR или WARN, а в канале errors их нет (должны приходить в течение 1 минуты). Либо правило Grafana сработало, а сообщения нет. Записи уровня INFO оповещений не вызывают, так задумано.

**Проверить.**

1. Жив ли Mattermost: с ВМ 1 `curl -i http://<IP_ВМ2>:8065/api/v4/system/ping`. Если нет, это инцидент по ВМ 2, а Grafana тоже не сможет написать в канал.
2. Работает ли вебхук:

```
curl -X POST -H 'Content-Type: application/json' -d '{"text":"проверка вебхука"}' '<адрес_вебхука>'
```

Сообщение появилось в канале: вебхук рабочий. Ошибка 404 или отказ: вебхук удалён, отключён или канал изменён (Mattermost: Интеграции, Входящие вебхуки).

3. Верен ли адрес в настройках: `grep -i webhook .env` на ВМ 1 и точка оповещения в Grafana. Пустой адрес в логах API выглядит как сообщение, что WebhookUrl не настроен.
4. Не закрыт ли в ufw порт 8065 на ВМ 2 для ВМ 1.

**Сделать.** Создайте новый вебхук и замените адрес в двух местах (`.env` на ВМ 1 и Grafana) по пункту 5 Инструкции администратора, перезапустите API. Проверка: тестовое сообщение пришло в канал.

**Отвечает.** Икромжонов Ш. (Mattermost, вебхук), Жидкова В. (`.env` на ВМ 1), Иванова А. (Grafana).

## Инцидент 6. Упала ВМ 3

**Признак.** Grafana (`:3000`) не открывается, оповещения не приходят, новые файлы копий не появляются. Последствия: ВМ 1 и ВМ 2 никто не контролирует, копии БД не делаются, а прежние копии лежат только на ВМ 3.

**Проверить.** `ping <IP_ВМ3>`, статус ВМ в консоли BASIS. После входа: `docker compose ps`, `df -h /`, `crontab -l`, `ls -lt <КАТАЛОГ_КОПИЙ> | head -n 3`.

**Сделать.**

1. Запустите или перезагрузите ВМ в BASIS, затем `docker compose up -d` в каталоге мониторинга.
2. Сразу сделайте копию вручную: `~/IT-workshop/backup/backup.sh`, и убедитесь, что расписание на месте (`crontab -l`).
3. В Grafana проверьте, что все цели UP, и отправьте тестовое оповещение.
4. Пока ВМ 3 недоступна, проверяйте сайт и Mattermost вручную (пункт 1 Инструкции) и при необходимости снимайте копию БД на свой компьютер, а не на ВМ 1:

```
ssh <пользователь>@<IP_ВМ1> 'docker exec <БД> pg_dump -U loghive LogHiveDB | gzip' > loghive_$(date +%F_%H%M).sql.gz
```

5. Если ВМ 3 потеряна совсем, создайте её заново и разверните по пунктам 2.6 и 2.7 Инструкции. Метрики за время простоя и прежние копии будут потеряны.

**Отвечает.** Иванова А.; если её нет на связи, любой участник команды.

## Инцидент 7. Утёк ключ или пароль

**Признак.** Секрет попал в публичный репозиторий, чат, скриншот или логи. В панели чужие входы, в LogHive чужие записи, в канале чужие сообщения.

| Что утекло | Чем грозит | Где менять |
| --- | --- | --- |
| Ключ приёма записей (X-Api-Key) | Чужие записи в LogHive | `.env` на ВМ 1, агент на ВМ 2 |
| Адрес вебхука Mattermost | Чужие сообщения в канале | `.env` на ВМ 1, Grafana |
| Пароль БД | Доступ ко всем данным | ВМ 1 |
| Ключ JWT | Подделка входа в панель | ВМ 1 |
| Пароль root панели | Вход в панель | ВМ 1 |
| Пароль Grafana | Просмотр мониторинга | ВМ 3 |
| SSH-ключ копирования или пароль ВМ | Вход на ВМ | ВМ 3 и ВМ 1 |

**Сделать.** Сначала замена, потом разбор.

1. Определите, какой секрет утёк.
2. Сразу замените его по пункту 5 Инструкции администратора. Для ключа JWT все пользователи будут разлогинены, это ожидаемо.
3. Секрет, попавший в Git, считайте скомпрометированным навсегда: одной правкой файла не обойтись, история хранит прежнее значение.
4. Проверьте следы: `last` на ВМ, логи API за период утечки, неизвестные записи и сообщения.
5. Порядок работы с секретами описан в `docs/access-rules.md` репозитория.

**Отвечает.** Тот, кто заметил, сообщает владельцу ВМ сразу. Меняет секрет владелец ВМ, решение о масштабе принимает команда.

## Инцидент 8. Внезапно много ошибок

**Признак.** График ошибок в Grafana резко вырос, в канале errors поток оповещений, в панели LogHive растут счётчики групп.

**Проверить.**

1. В панели LogHive включите фильтр ERROR и период 1 час, найдите группы с самым большим счётчиком. Одинаковые записи склеены по уровню, тексту и источнику, так что повторяющаяся ошибка видна сразу.
2. Откройте группу: источник и время первого появления. Совпадает ли оно с обновлением или чьим-то сбоем.
3. Один источник или много. Источник Mattermost или другое приложение.
4. Загрузка процессора, памяти и диска ВМ 1 в Grafana: один процессор на ВМ 1 главный риск при пике записей.

**Сделать.**

- Ошибка пришла из Mattermost или его базы: проверьте ВМ 2 (`docker compose ps`, ping).
- Ошибка соединения с БД или сетью: инциденты 2 и 1.
- Ошибка появилась после обновления: откатите прежнюю версию.
- Одно приложение шлёт тысячи записей: свяжитесь с его владельцем, пусть остановит или исправит отправку.
- Растёт диск: инцидент 3. Канал errors завален: вебхук не отключайте, пока не найдена причина.
- Разобранную группу отметьте решённой в панели: если запись придёт снова, группа откроется заново.

**Отвечает.** Дежурный, затем владелец источника ошибки (разработчик приложения, для Mattermost Икромжонов Ш.).
